Article 50(2) · conformance teardown

What the C2PA marking actually shows — and what happens to it when you re-save the file

Three real files, taken as emitted by OpenAI, Google and Adobe. Ten local transformations, none of them a platform upload. Thirty runs, thirty strips. A visually-lossless JPEG re-save at quality 95 destroys the C2PA metadata layer on all three. Alongside the measurement, a byte-level read of the reference SDK turned up four findings and two null results. Everything below is re-runnable on your own files, on your own machine.

00 · scope

Read this before you quote a number from this page

Scope lock

This measures the C2PA metadata layer only. It cannot see SynthID, AudioSeal, or any imperceptible watermark. An invisible layer may survive every transformation below and this test would never know it was there.

PERMITTED
“the C2PA metadata layer does not survive a re-save”
FORBIDDEN
the same sentence with “the marking” in place of “the C2PA metadata layer” — we did not measure the other layer, so we may not speak for it

The EU Code of Practice asks for a multi-layer approach: metadata plus watermarking. We audit one layer. Saying otherwise would be the same overclaim this page exists to examine.

Three further limits, stated up front rather than buried:

  • This says nothing about whether a file is AI-generated. A C2PA manifest can carry the signer's declaration that content is AI-generated (a c2pa.created action with digitalSourceType: trainedAlgorithmicMedia), but that is a signed claim by the signer, not independent proof; the spec does not mandate it, so a valid manifest may omit it and its absence proves nothing. A manifest records who asserted what, not whether the assertion is true. This tool reads the signed record; it is not a detector.
  • No vendor here is doing anything wrong. All three sign correctly. The marking is well-formed in every case. It is stripped because the layer it lives in is stripped.
  • This is not a survey. Three files, one per vendor, one date. Vendors change their pipelines without announcing it. The date on this page is load-bearing.

Three vendors. Three signers. Two claim versions. Three different revocation mechanisms. Identical result.

Not one of these is a platform upload. Every one is routine inside a CDN, a CMS, or a publishing pipeline — the ordinary machinery a file passes through between a generator and a reader. A JPEG re-save at quality 95, which is visually lossless, is enough on its own.

Adobe founded C2PA, and their output behaves exactly like everyone else's here. That is the reason to read this as a property of the layer rather than as one vendor implementing it badly. The specification is candid about it: removal is not something the format protects against.

02 · vocabulary

The ladder, and why there is no single green tick

Most tools collapse a C2PA manifest into one word. That word does the work of hiding several distinct questions, which have several distinct answers. The tool used here refuses to aggregate. It reports each leg separately, in the words below — and the page and the tool use the same words, deliberately.

legstatuswhat it establishes
hash binding VERIFIED A decidable check: the bytes are unchanged since signing. Nothing more.
signature VERIFIED The holder of this certificate signed these bytes. Not who they are. Not that the content is true.
trust chain VERIFIED / UNTRUSTED Whether the chain reaches a root on a trust list. A policy fact — and it depends on which list. See F2.
revocation NOT_REVOKED / REVOKED / INACCESSIBLE / SKIPPED / NOT_CHECKED_SILENTLY Whether the certificate is still good today. Five outcomes, and the SDK never emits one of them. See F4.
timestamp ANCHORED / SELF_ASSERTED Whether a timestamp authority signed the time, or the signer simply asserted a date. For claim v1, see F5.
assertions REPORTED What the signer wrote. Zero evidentiary weight about the physical world. A C2PA camera has signed AI output before — the Nikon Z6 III.
AI-generated? NOT_ANSWERED Out of scope. No manifest can answer it, and neither can we.
On the word VERIFIED

A signature check is decidable over a finite, already-committed set of bytes: it holds by construction. That is a different class from a statement quantified over every path a system could take, established before it runs. Both are worth having. Calling them by the same word is how a reader ends up believing the weaker one is the stronger one, and this page does not have a second word to spare.

03 · findings

Four findings from the SDK, each with a citation you can check

These came out of reading c2pa-rs line by line, not out of watching its output. That distinction is the whole method, and it is the reason two of my earlier claims did not survive (see N3).

F2
There is no single answer to “is this trusted?”

Same Adobe file. Same SDK. Same day. Two official trust lists:

OFFICIAL C2PA trust list  →  Valid    failure=[signingCredential.untrusted]
INTERIM trust list (ITL)  →  Trusted  failure=[]

Both lists are official. They disagree. And by the CAI project's own documentation — the path is inside c2pa-rs itself — the Adobe Content Authenticity Inspect tool reads the official list, while the C2PA Verify tool reads the interim one. Two Adobe verification tools return different trust verdicts for Adobe's own file.

Adobe is not doing anything wrong. Firefly chains to Adobe Root CA G2, an ITL-era credential, and content signed under an ITL certificate stays valid against the legacy trust model by design. The problem is not the signer. It is the verifier. Ask “is this trusted?” and the honest answer is a question back: which list are you holding?

Article 50(2) asks for marking that is effective, interoperable, robust and reliable, and it applies in full from 2 August 2026. The 2 February 2027 deadline for interoperable detection is not in the Regulation: it is Measure 3.4(c) of the Code of Practice on Transparency of AI-Generated Content, a voluntary instrument that binds only its signatories and that states adherence to it is not conclusive evidence of compliance. If two official lists split on the same file, interoperable is not yet a property of this ecosystem.

source  c2pa-rs  cli/docs/usage.md:287-288
F3
c2pa-rs bundles no trust list, so out of the box nothing can ever be trusted
NO_TRUST_LIST_BUNDLED_SO_NOTHING_CAN_EVER_BE_TRUSTED
SPEC_STATE_VALID_TOLERATES_UNTRUSTED_CREDENTIAL

The include_bytes! calls in certificate_trust_policy.rs sit behind #[cfg(test)]. They are compiled into the test binary and not into the library. Out of the box, no file reaches Trusted — measured on all three vendors, including genuinely signed ones.

So a developer running the SDK as shipped, against a real OpenAI image, sees Valid. And Valid is also what a self-signed forgery produces, carrying the same signingCredential.untrusted failure code.

The objection, and the answer

“User error. You did not configure trust. Same as skipping certificate validation in TLS.”

It would land if the state were called SignatureOK, or Unverified. It is called Valid, and in every other API valid means good. The developer who checks state == "Valid" is making the natural check and is conformant with the specification: validation_state() deliberately admits failures when the only failure is signingCredential.untrusted, with a source comment pointing at the spec's own #_valid_manifest anchor. The SDK does exactly what the spec says. The word is doing the work of hiding the gap.

Two disanalogies with TLS, both checkable, and both cutting the other way. TLS fails closed: there is no state that means “the crypto is fine, the signer went unchecked.” And every mainstream TLS stack ships a root store. c2pa-rs ships none.

This is also why the Krawetz forgery walked past every tool except the Content Credentials site: that site loads a list. By default, nothing else does.

F4
A revocation code that is defined, documented, tested — and never emitted
OCSP_SKIPPED_CODE_DEFINED_BUT_NEVER_EMITTED
Concession first, and it is load-bearing

ocsp_fetch: false is the correct default. The CAI security policy lists network calls driven by C2PA manifest input as a known problematic characteristic, with work in progress under a tracking issue. Not making outbound requests on attacker-controlled input is good engineering. The default is right. The finding is its consequence.

Four revocation states are defined. Three are emitted.

codestatussite
ocsp.revokedemittedocsp.rs:133, :266
ocsp.notRevokedemittedocsp.rs:151, :284
ocsp.inaccessibleemittedocsp.rs:435
ocsp.skippednever—

The fourth is defined at validation_results.rs:642. It carries a doc comment — the validator chose not to perform an online OCSP check. It is classified Informational by log_kind(). It is placed into output by a serialization unit test. And it is emitted from no validation path anywhere. It is not even imported into ocsp.rs.

On the default path the code returns Ok(OcspResponse::default()) and logs nothing. That struct's revoked_at is None — structurally identical to a successful check that found no revocation. Absence of evidence, returned in the shape of evidence of absence. The caller cannot tell “checked, certificate live” from “never checked”: not in the state, not in validation_results(), not in the returned struct.

The SDK anticipated this code in its own output. The emission site is simply missing. That reads as an oversight rather than a decision, and the fix is one line in the DoNotFetch arm.

Where it bites, measured

OpenAI checks revocation through a cert-status assertion; Google through a COSE staple, by elimination. Both come back notRevoked. But both mechanisms are a snapshot taken at signing time. Revocation that happens after signing stays invisible either way — which is consistent with the spec's stated intent that a manifest validate indefinitely, and is worth knowing before anyone leans on the word.

F5
A timestamp is affirmed as trusted with the trust check skipped — on current, production Adobe output
TIMESTAMP_TRUSTED_ASSERTED_WITHOUT_CHECK  ·  claim v1 only
Concession first

The skip is defensible. store.rs:1952 passes verify_trust = rc.version() != 1, commented — in the source's own typo — “no trust checks for leagacy timestamps.” Backward compatibility for v1 claims. Declining to trust-check a legacy timestamp is a reasonable choice. The skip is not the bug.

The bug is that timeStamp.trusted lands in the success bucket anyway. A brace-depth trace of time_stamp/verify.rs shows the guard if verify_trust { opening at line 535 and closing at 583 — while TIMESTAMP_TRUSTED is emitted at line 590, at depth zero. Outside the guard.

Empirically it fires with full trust lists loaded, with zero anchors, and with trust verification switched off entirely. Unconditional. For a claim-v1 manifest the SDK therefore affirms that a timestamp certificate is trusted having performed no trust check.

This is not silence, as in F4. It is a positive assertion in the success bucket, which makes it the stronger of the two. And in both findings the shape is the same: the signal for “we did not check” is the thing that is missing.

Where it bites, measured — and the qualifier that must never be dropped

OpenAI and Google emit claim v2. The check runs. It does not trigger. Adobe Firefly emits claim v1 — so on current, production Adobe output, timeStamp.trusted sits in the success bucket with the trust check skipped. This finding is scoped to claim version 1 and it is stated no other way.

source  store.rs:1952 (verify_trust = rc.version() != 1)
         crypto/time_stamp/verify.rs:535 (guard opens), :583 (guard closes), :585-591 (emitted outside it)

F6
Adobe OCSP silence — observed, not explained

With OCSP fetching explicitly enabled, c2pa-rs emits no revocation code at all for Adobe Firefly output. Not notRevoked. Not inaccessible. Nothing.

And yet, all four of these hold at once:

  • the Adobe leaf certificate does carry an OCSP responder URL — ocsp.one.digicert.com, extracted with c2patool --certs;
  • that responder, queried directly with openssl ocsp, answers good;
  • the fetch path in the SDK works — the same build emits inaccessible for a test certificate whose responder is unreachable;
  • fetching was switched on.

Live responder. Working fetch path. A certificate with a URL. Fetch enabled. And silence.

I did not find the cause in the source, and I am not going to name one. This is an open observation, and it stays an observation until someone reads the path that explains it. If that someone is you, the issue tracker is at the bottom of this page.

04 · null results

The things that did not hold

A teardown that reports only its hits is not evidence. It is advocacy. These are the reason to believe the findings that survived.

N1

The ingredient case does not bite

I expected F5 to reach through ingredients. A claim-v1 ingredient sitting inside a v2 manifest is exactly what an edit-history workflow produces, and it looked like the dangerous case: a file that reads as modern while carrying a legacy claim.

I constructed that file — a v2 active manifest carrying the c2pa-rs v1 fixture as a parentOf ingredient — and tested it. It does not bite. The reader emits only ingredient.manifest.validated, meaning the hash matched, and that is unchanged with or without trust anchors loaded. It checks that the ingredient was not altered. It does not re-verify the ingredient's signature, timestamp, or trust chain at read time.

Negative result, stated plainly, and stated here rather than quietly dropped.

N2

My prediction was wrong, and it was written down before the run

I wrote an expectation lock before the vendor run, so that it could not be rationalised afterwards. It said the SDK findings would hold regardless of vendor.

It was wrong. F4 and F5 both failed to appear on OpenAI and Google, and surfaced only on Adobe — which I had not anticipated at all. The vendor axis turned out to matter more than the SDK axis, and I would not have discovered that if the prediction had not been on paper first.

N3

Method: the source killed several of my own claims

Byte-level review of c2pa-rs falsified more than one thing I had already written down — including two false values that my own tool printed into a results table, because it searched for a status-code string that does not exist in the SDK. It reported UNRESOLVABLE and no staple on files where the SDK had in fact checked revocation and found it clean.

Every one of those failures came from the same place: an inference drawn from output, instead of a read of the source. The exact strings are now pinned in the tool with the line numbers they came from. That is the correction, and it is the reason to trust the numbers above rather than a reason to discount them.

05 · boundaries

What this does not show

Not that AI content is undetectable

This page says nothing whatever about whether a given file is AI-generated. A C2PA manifest can carry the signer's AI-generation declaration (c2pa.created with digitalSourceType: trainedAlgorithmicMedia), but that declaration is a signed claim by the signer, not independent proof: it is only as reliable as trusting that signer, it is optional under the spec, and its absence means nothing. A manifest records who asserted which label, not whether the label is true — the same way a watermark is only valid in the context of whoever applied it. This tool reads the signed record; it does not adjudicate the claim.

Not that any vendor is failing its obligations

All three sign correctly. Adobe's ITL-era certificate is valid under the legacy trust model by design. OpenAI and Google both check revocation. The marking is well-formed in every case. It is stripped because the metadata layer is stripped. Note on scope: the SDK-level findings below are behaviours of the c2pa-rs 0.89.0 / c2pa-python 0.36.0 implementation that was measured, not statements about the C2PA specification itself, which produces no reference implementation.

Not that the other layer fails

The watermark layer was not measured. SynthID, AudioSeal, or any imperceptible mark may survive every transformation on this page, and this test would never know. The Code of Practice asks for metadata and watermarking. We audited one of the two.

Not a survey

Three files. One per vendor. One date: 12 July 2026.

Regulatory status — the dates, not the durations

Article 50 transparency obligations apply from 2 August 2026.

Article 50(2), the machine-readable marking obligation, applies from 2 December 2026 for systems already on the market. The Digital Omnibus on AI published on 24 July 2026 as Regulation (EU) 2026/1744 (OJ L, 2026/1744, 24.7.2026) and enters into force on 27 July 2026, the third day following publication. That 2 December 2026 date is not a deferral of Article 50(2) itself: Article 50 applies from 2 August 2026, and the Omnibus inserts a new Article 111(4) giving providers whose systems were placed on the market before that date until 2 December 2026 to comply.

Updated 25 July 2026. This paragraph previously said the Omnibus had not reached the Official Journal and that the date above could change before you finished reading it. It has now published, and the date above is read from the enacted text rather than predicted from a draft. Check the OJ yourself before you rely on any date here.

Note the phrasing throughout. Published legal commentary describes the same Article 50(2) grace period as three months in one firm's note and four months in another's, while both land on 2 December 2026. When the commentary cannot agree on the duration, the duration is being reconstructed rather than read. Take the date.

06 · reproduce it

Run it against your own output

This is the section that makes the page evidence rather than an opinion. Everything above is a claim about bytes. Here are the bytes.

# 1. the tool
curl -O https://nous-lang.org/a50/a50_teardown.py
sha256sum a50_teardown.py
#   expect: 5ad5570344ad48b462e353409a3a770a443812016ec5c72062282e1ebc64ece4

# 2. the dependencies
pip install c2pa-python pillow

# 3. the trust lists (the SDK bundles none -- see F3)
git clone --depth 1 https://github.com/c2pa-org/conformance-public.git conf
cp conf/trust-list/C2PA-TRUST-LIST.pem     .
cp conf/trust-list/C2PA-TSA-TRUST-LIST.pem .

# 4. run it. both lists load from the working directory.
python3 a50_teardown.py your_image.png

# reproduce the SHIPPED SDK instead -- no trust list, no OCSP fetch:
python3 a50_teardown.py your_image.png --no-trust-list --no-ocsp

# machine-readable output
python3 a50_teardown.py your_image.png --json out.json --md out.md

The defaults in this tool are the opposite of the SDK's: trust lists on, OCSP on. That is deliberate. --no-trust-list and --no-ocsp reproduce what a developer sees running c2pa-rs as shipped, which is the demonstration behind F3 and F4. Run it both ways on the same file and the gap is the finding.

If no trust list is present, the tool says so and warns that every result is untrusted by configuration rather than by evidence. A run in that state is not a run whose numbers may be published, and the tool tells you as much in its own output.

On the hash above

Checking a hash published on this site against a file downloaded from this site tells you very little — anyone holding this host could serve both. That hash is worth something when you obtain the script from somewhere else, or when you want to state which bytes produced a result you are quoting. It is a pin, not an assurance, and it is published as a pin.

The run is deterministic: same input, same corpus version, same output. What is published here is the script, its hash, the exact library versions, the corpus version, and which trust list was loaded. That set is what makes a third party able to disagree with me on the evidence rather than on my say-so.

Nothing is uploaded. There is no backend, no endpoint, no form. The script runs on your machine, on your files, and the tool that tells you not to trust unverifiable claims does not ask you to trust it with your images.

The script is open and it runs on your own machine. If you want this run against your own output, with the result signed and independently reproducible by a third party — ask.
